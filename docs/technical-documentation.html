Technical Documentation

Purpose and scope

ScholarDesk implements the selected student information and task management project. It provides student CRUD, task CRUD, deadline monitoring, search, submission status, and a dashboard. It runs locally with PHP from XAMPP and a persistent SQLite database. The interface uses local CSS and JavaScript with no external libraries or online assets.

Architecture and data flow

Browser interface (public/index.php + assets/app.js)
    ↓ same-origin JSON requests
HTTP adapter (public/api.php)
    ↓ validated use-case calls
Application layer (SchoolService)
    ↓ validation / status policy       ↓ PDO operations
Domain layer (Rules)                Infrastructure (Database)
                                        ↓
                                 data/scholardesk.sqlite

The domain has no dependency on the interface, database, or web server. The interface communicates through the HTTP adapter. Infrastructure creates the PDO connection and schema; the service receives that connection in its constructor. The small application keeps SQL within the service to avoid unnecessary repository classes; this is a pragmatic layered design rather than a complete enterprise Clean Architecture framework. A future refactor can introduce repository interfaces if more storage backends are needed.

Domain model

EntityIdentity / attributesRules
Studentid; student_number; full_name; email; course; year_level; section; created_atStudent number and email are separately unique, case insensitive. Six user fields required; year 1–6.
Taskid; title; subject; due_date; description; created_atTitle and subject required; valid calendar date required; optional description. Shared with every student.
SubmissionComposite primary key (student_id, task_id); submitted_atAt most one record per pair; foreign keys cascade on deletion. Existence means submitted; absence means pending or overdue.
Student 1 ───── 0..* Submission 0..* ───── 1 Task
(All Student × Task pairs exist logically; only submitted pairs are stored.)

Student and Task are identified domain concepts represented as validated data arrays. Submission models the relationship. This applies DDD vocabulary and invariants at the scale of a small classroom system, without claiming full strategic DDD or separate bounded-context services.

Important decisions

  • SQLite: available in installed XAMPP PHP; avoids MySQL service setup. The PDO adapter and schema would need changes for a MySQL version.
  • Private data folder: only public/ is served. Database, source, tests, session files, and Git history are not HTTP resources.
  • Derived status: overdue is calculated at read time from the Manila calendar date. No scheduled job or stale stored overdue flag is needed.
  • Idempotent submission: repeating a submitted request preserves the original timestamp. Marking pending removes the stored submission.
  • Automatic assignment: all students receive all tasks. There is no enrollment or per-student assignment feature.
  • Demo seeding: a transaction creates fictional records and refuses to run on a nonempty workspace.

Validation and error handling

Server rules trim strings, enforce field length, check email format, reject fractional/out-of-range years, and reject impossible dates. Prepared statements bind user values; SQL table names come from a fixed allowlist. Duplicate database constraints become HTTP 409 errors. Missing records become 404; validation failures become 422; invalid session tokens become 403. Unhandled failures are logged without sending internal paths or traces to the browser.

Local protection and limitations

Browser output is escaped before insertion; the page has a restrictive Content Security Policy. Writes require a per-session CSRF token and JSON content type. Cookies are HttpOnly and SameSite Strict. The launcher binds only 127.0.0.1. This is a single-operator local demonstration with no authentication or roles. CSRF is not a login system. Do not expose the PHP development server to a network. Pagination, concurrent-user/load behavior, accessibility audits, authentication, and production deployment remain outside validation.

Development environment

Verified on Windows with XAMPP PHP 8.2.12, PDO SQLite and mbstring enabled; Python 3.14 for optional black-box HTTP tests; Git and Visual Studio Code installed. No framework or external package installation was needed. Development and verification were assisted by AI; group members should study, modify, and explain the implementation.

Extension guide

To add a field, update the domain validator, database schema/migration, HTML form definition in app.js, API examples, and meaningful tests. To use MySQL, introduce an appropriate PDO adapter and migrations and replace SQLite-specific SQL such as INSERT OR IGNORE. To add per-course tasks, model enrollment explicitly and replace Student × Task assignment calculations.
